# Design the learning, not just the deck

Start with a meaningful phenomenon or task. Let the learner manipulate it, predict, and see the need for an explanation. Return to that original question after formal developments.

Breadth provides a map of the mechanism, uses, alternatives, assumptions, and limits. Depth traces a representative example through the entire argument. Avoid both a catalogue of facts and a proof detached from purpose.

A useful pattern is concrete case -> visible operation -> named quantity -> symbolic rule -> justification -> new prediction -> limit or transfer. Adapt it; do not mechanically repeat a template on every slide.

Budget the central mechanism, proof, applications, and transfer before prerequisites. Refreshers should normally take a minority of learning time and immediately enable a target operation. Do not put the promised core derivation in an appendix because setup consumed the budget.

## Scene contract

Specify the learner's question, intended inference, starting mental model, exact new idea, concrete example, units, stable labels, prediction before feedback, manipulation, changing quantities, invariants, causal explanation, misconception addressed, short check, and next question.

A difficult transition may span several slides. A slide can also pause for reading or proof. Do not force widgets onto every sentence. The important mechanisms need meaningful manipulation, with enough variety that one slider is not repeated beside unrelated equations.

## Background at the point of need

Map prerequisites privately; show learners a simple route of questions. Each refresher explains “We need this now to do X,” gives one example, and immediately uses it in X. Preserve the current scene when opening optional background. Define symbols, dimensions, indices, and conventions before use.

Teach operations through their purpose. A transpose pairs columns; a constraint makes comparisons fair; a derivative measures the effect of a small change. Do not introduce a name before the learner has a reason to care.

## Earn each mathematical step

Show the current expression, target question, operation, reason it is valid, assumptions, dimensions, and meaning for the original problem. Include a numerical or geometric witness where useful. Keep the previous expression visible when comparison matters.

Distinguish definitions, identities, observations, approximations, theorems used without proof, stationary conditions, and global guarantees. A local condition is not a global proof. Numerical agreement illustrates an identity; it does not prove it for all inputs.

Progressive reveals should follow algebraic changes and their visual meaning. Interactive values must agree across equations, labels, diagrams, and metrics. Label a fixed worked example separately if it does not follow the control.

## Visual explanation

Choose representations that suit the topic: accurate geometry, repeated trials and distributions, evidence comparison, causal alternatives, or system-state traces. Do not turn all subjects into angle sliders or bar charts.

Use large informative figures, readable labels, stable semantic colors, equal scales where required, honest units, and text near the object it explains. Compare original and changed states when that comparison teaches the idea. Provide reset and keyboard paths. Preserve useful state across refreshers and navigation, or disclose resets.

An interaction should support prediction -> manipulation -> observation -> explanation -> a new case. Include surprising contrasts and failures. A control that changes a number without revealing a relationship fails the scene contract.

## Lesson from PCA

Begin with the cloud, retained axis, score line, and lost detail. Ask which direction preserves important differences. Then derive a measure: center -> score -> squared spread -> cross-products -> covariance -> objective -> optimal direction -> global proof -> reconstruction -> limits.

The current PCA draft still needs a dedicated tangent/normal visual for the gradient-to-eigenvector transition and explicit row/column pairing for the transpose product. Several scenes repeat an axis control without a distinct explanatory action. These are examples of failed scene contracts, not requirements that every subject copy the PCA sequence.
