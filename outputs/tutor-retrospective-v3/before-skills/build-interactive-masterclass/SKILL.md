# Build an interactive masterclass

The goal is a usable mental model: the target learner can explain why the idea matters, predict with it, justify its key steps, apply it without copying, and recognize its limits. Retention requires later evidence. Length, correct equations, attractive screens, and working controls establish different things.

This is the canonical teaching process, version 2. `build-intuition-masterclass` is a compatible entrypoint, not a second process to run.

## Choose scope before acting

Recover purpose, audience, available learning time, required depth, format, feedback, and useful existing work. Age is not prerequisite evidence. Ask only for unknowns that materially change the route; otherwise label assumptions.

- **Brief answer / small edit:** do it directly and check the affected claim. Do not start a course pipeline.
- **Plan:** research and inspect the route on paper; stop before implementation.
- **Retrospective / skill update:** inspect evidence, challenge causes, revise the process, and test it in isolation. Do not change the lesson or start its rebuild.
- **Build / substantial redesign:** use the loops below. An internal gate is not a new permission request. An explicit user review-before-build instruction is a pending dependency.

Honor the chosen medium. Prefer native marimo-studio for this user's notebook/slide requests; read [the adapter](references/marimo-studio.md) for that medium. Do not silently replace it. Preserve a working visual baseline until a representative comparison supports changing it.

## Outer loop: choose a strategy that survives a pilot

Read [research and comparison](references/research-debate.md) and [the harness contract](references/harness.md) for substantial work.

1. **Define purpose and evidence.** State the learner's real problem or intellectual puzzle, what the lesson enables, and the central question. Define prediction, explanation/argument, application, boundary, and transfer tasks appropriate to that promise. Identify the hardest inference before allocating effort.
2. **Inspect contrasting explainers.** Compare substantive explanations and an authoritative subject source. Record material actually accessed. Titles, snippets, and transcripts do not establish animation quality. Extract teaching moves and their limits; do not copy a script.
3. **Propose two serious routes.** Obtain separate proposals before sharing the preferred route where agents are available. Give each a strongest objection and a discriminating pilot. Decide with reasons, not vote count. Label author-informed or same-context reviews honestly.
4. **Make a compact inference route.** Follow [lesson design](references/lesson-design.md). Connect the initial model to the promised capability. Attach needed background to the step it unlocks. Reserve the central argument and transfer before adding refreshers or polish.
5. **Pilot before expansion.** Test an opening that earns the goal, the hardest representation-to-reasoning bridge, and a fresh application or failure case. Include immediate prerequisites and next use. Check the medium's feasibility early. A polished introduction does not validate a proof route.
6. **Keep, revise, or abandon the route.** Use learner-visible evidence and [review standards](references/review.md). Record what could falsify the choice. User rejection reopens the affected decision. Permit provisional expansion at the stated review level; do not pretend unavailable human evidence exists.

The aim to exceed an expert tutorial is a benchmark hypothesis, not a release adjective. Match audience, goal, depth, time, and assessment. A longer course with more controls has not thereby won.

## Inner loop: earn one conceptual inference

For each difficult bridge: identify the question and likely wrong model → choose a discriminating example or worked explanation → produce the learner-visible scene → obtain an uncoached attempt on a new case → inspect reasoning and attention burden → make one causal repair → recheck that obligation.

Use direct instruction when knowledge is missing. Do not turn every scene into a guessing game. A useful interaction tests a belief, compares alternatives, exposes a mechanism, supports construction, or diagnoses failure. Software doing the calculation is not evidence that the learner inferred the relation.

Show why each new representation or operation serves the original purpose. Connect symbols to objects, track assumptions and invariants, and distinguish examples from proof. Preserve requested rigor. More algebraic lines do not automatically explain why those lines solve the problem.

Default to at most two unsuccessful causal repairs to the same inference before reopening the strategy or representation. This is a work limit, not a learning law. Rendering repairs have separate findings. Do not erase failure by renaming an issue. Declare bounded research, pilot, repair, and verification allocations; do not invent a user token allowance. At a cap, preserve the draft and provide the diagnosis and exact next test.

## Separate authoring from tutoring

Authoring loops design the experience. The learner runtime loop is different: diagnose readiness → explain/model as needed → attempt → response-specific feedback → unaided retry → new case → later retrieval if in scope. Read [adaptive tutoring](references/adaptive-tutoring.md) only for branches, live tutoring, or stateful feedback.

A static course may contain authored branches. A planning file is not a deployed adaptive tutor. A correct number with a wrong explanation, assisted success, and independent transfer are different evidence.

## Review and deliver

Use separate correctness, teaching, visual/interaction, and runtime checks. Reviewers cite a scene, observed behavior, learner consequence, and repair test. Include a cold whole-route walkthrough; many locally valid steps can still lose the main question. Preserve consequential disagreement.

At least one unfamiliar-context review should receive learner-facing material without the author's diagnosis where available. Otherwise disclose the limitation. Require the reviewer to cite the visible warrant for each inference; a knowledgeable AI can solve a task from prior knowledge despite a bad lesson.

Keep claims separate: software verified; explanation reviewed; simulated learner reviewed; human learner observed; comparative learning tested; delayed transfer tested. Never promote the first three into the last three. The CLI checks registered records and dependencies; it cannot verify truth or prevent direct tool edits.

Deliver source, launch/navigation instructions where relevant, current evidence, and the strongest remaining limitation. For this user's 80% ASD-STE100 target, apply [review standards](references/review.md); sentence length alone is insufficient.

Update this process from demonstrated failure or useful forward tests. Test substantial changes on unfamiliar quantitative and nonmathematical bridges plus scope/stop cases. Publish outputs and provenance. Prefer a simpler process if added machinery does not improve the result.
